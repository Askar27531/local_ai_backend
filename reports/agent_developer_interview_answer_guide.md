# Agent 开发岗位面试回答指南

这份文档面向公司常见的 Agent / LLM 应用开发岗位面试问题。它不是只列问题，而是告诉你每类问题应该怎么回答，并尽量给出可以结合 `npc_app` 项目的说法。

## 回答总原则

面试时不要只说“我用了 LangChain、LangGraph、RAG、Milvus”。更好的回答结构是：

1. 先说业务目标。
2. 再说技术方案。
3. 再说为什么这样设计。
4. 最后说当前不足和下一步优化。

推荐模板：

> 这个问题我会从场景、架构、权衡和改进四个角度回答。我的项目里是一个游戏 NPC 对话 Agent，核心目标不是让模型完全自由行动，而是在剧情、人设和记忆边界内稳定回答。所以我用受控 workflow 编排模型能力，用数据库和 Milvus 管理跨轮记忆，用 prompt 和检索过滤控制 NPC 可见信息。

## 1. 什么是 Agent？和普通 Chatbot 有什么区别？

**面试官想听什么**

- 你是否理解 Agent 不是简单聊天。
- 你是否知道 Agent 通常包含目标、状态、工具、记忆、规划和执行。
- 你是否能说清什么时候不该用 Agent。

**回答框架**

- 普通 Chatbot：输入问题，模型直接生成回答。
- Agent：有目标，有状态，能调用工具，能根据环境反馈继续行动。
- 但 Agent 不一定越自主越好，生产环境经常需要受控 workflow。

**示范回答**

> 普通 Chatbot 主要是一次性的文本生成，而 Agent 更像一个带状态的执行系统。它会根据任务目标维护上下文，必要时调用工具，读取外部数据，并根据结果决定下一步。我的理解是，Agent 的关键不是“用了某个框架”，而是系统是否具备感知上下文、决策、行动和反馈闭环。  
>  
> 不过在生产系统里，我不会盲目追求完全自主 Agent。比如我的 NPC 项目更适合受控 workflow Agent，因为游戏场景有剧情边界、人设一致性和不可剧透要求。让模型完全自由规划，反而会增加风险。

**结合 npc_app**

> `npc_app` 里用户请求不是直接给模型，而是先加载线程、最近对话、长期记忆和 RAG 知识，再由 LangGraph 编排检索、构建 prompt、生成回答。

## 2. Workflow 和 Agent 有什么区别？

**面试官想听什么**

- 你能否区分确定性流程和模型自主决策。
- 你是否知道工程落地中 workflow 往往更稳定。

**回答框架**

- Workflow：流程固定，节点顺序明确。
- Agent：模型可以决定下一步做什么、调用什么工具。
- 实际项目可以混合：外层 workflow 控制边界，内部局部 Agent 做决策。

**示范回答**

> Workflow 更像固定管线，例如先检索、再构建 prompt、再生成回答。Agent 则更强调模型根据当前状态选择下一步，比如决定是否检索、调用哪个工具、是否需要追问用户。  
>  
> 我倾向于在高风险或强规则场景里优先用 workflow，把不可控部分压缩到有限范围。比如 NPC 对话里，剧情解锁、用户隔离、RAG 过滤这些都应该由代码确定性处理，模型主要负责语言生成和有限推理。

## 3. LangGraph 的 state 是什么？

**面试官想听什么**

- 你是否理解 state 是节点之间的数据载体。
- 你是否知道 state 和长期记忆、checkpoint 不是一回事。

**回答框架**

- State 是图执行时各节点共享和更新的数据结构。
- 节点读取 state，返回增量更新。
- State 可以包含用户请求、消息、工具结果、检索结果、错误信息。
- 如果接入 checkpoint，state 可以跨中断恢复；不接入则主要是单次执行内流转。

**示范回答**

> LangGraph 的 state 可以理解成一次图执行过程里的结构化上下文。每个节点从 state 读取需要的信息，处理后返回部分字段更新。比如一个 RAG Agent 的 state 可以包含 user question、retrieved chunks、tool results、final answer 和 error。  
>  
> 需要注意的是，state 不等于长期记忆。长期记忆通常要落到数据库或向量库，支持查询、审计和权限控制。state 如果没有 checkpoint，更多只是一次执行中的临时数据。

**结合 npc_app**

> `npc_app` 的 `NpcGraphState` 里有 `request`、`dialogue_history`、`summary`、`memory_items`、`chunks`、`system_prompt`、`user_prompt`、`answer` 等字段，用来串起检索、构建 prompt 和生成回答三个节点。

## 4. 为什么要用 checkpoint？什么时候不用？

**面试官想听什么**

- 你知道 checkpoint 保存的是图执行状态。
- 你能区分 checkpoint 和业务数据库。

**回答框架**

- 用 checkpoint 的场景：中断恢复、人工审批、多步任务、失败重试、长任务。
- 不用 checkpoint 的场景：每次请求短小、一次执行完成、业务记忆已由数据库负责。
- checkpoint 不是替代业务数据表的万能记忆库。

**示范回答**

> checkpoint 主要用于保存图执行状态，比如 Agent 运行到某个节点需要等待人工审批，或者任务执行失败后想从中间节点恢复。  
>  
> 如果系统每次请求都是短流程，并且执行完就把业务结果写入数据库，那不一定马上需要 checkpoint。我的 NPC 项目目前就是这样：一次聊天请求内完成检索、prompt 构建和生成，跨请求记忆由聊天记录、线程摘要、长期记忆表和 Milvus 负责。所以 checkpoint 可以作为后续复杂多步 Agent 的增强点，而不是当前必需项。

## 5. RAG 的完整流程是什么？

**面试官想听什么**

- 你是否能从数据处理讲到生成。
- 你是否知道 RAG 的问题不只在向量检索。

**回答框架**

- 数据准备：清洗、切块、元数据。
- 索引：embedding、向量库、关键词索引。
- 查询：query rewrite、embedding、召回。
- 后处理：过滤、rerank、去重、权限控制。
- 生成：把检索结果放进 prompt。
- 评估：检索相关性和回答正确性。

**示范回答**

> RAG 不是简单把文档丢进向量库。完整流程包括文档清洗、chunking、metadata 设计、embedding 入库；查询时要做召回、过滤、rerank 和上下文预算；生成时要明确告诉模型只能基于可用资料回答；最后还要评估检索是否命中、答案是否忠实。  
>  
> 真正落地时，metadata 非常关键。比如我的 NPC 项目里，文档不只是文本，还要带 NPC、剧情解锁等级、主题等信息，否则很容易检索到玩家当前不该知道的内容。

## 6. chunk size 和 overlap 怎么选？

**面试官想听什么**

- 你知道这是权衡问题，不是固定答案。
- 你能说出评估方法。

**回答框架**

- chunk 太小：上下文不完整。
- chunk 太大：噪声多、成本高、召回不准。
- overlap：保证跨段语义连续，但会增加重复。
- 最终通过 retrieval eval 和 answer eval 调参。

**示范回答**

> chunk size 取决于文档结构和问题粒度。FAQ 或短知识点可以小一些，长叙事、规则说明可以大一些。overlap 用来避免关键信息被切断，但过大会造成重复召回。  
>  
> 我不会只凭经验定死，而是会构造一组典型问题，看正确 chunk 是否能被召回，再看模型回答是否完整。如果召回片段经常缺上下文，就增大 chunk 或增加结构化标题；如果噪声太多，就缩小 chunk 或增强 rerank。

## 7. 向量检索、关键词检索和 hybrid search 有什么区别？

**面试官想听什么**

- 你理解不同检索方式的适用场景。

**回答框架**

- 向量检索：语义相似，适合同义表达。
- 关键词检索：精确匹配，适合专有名词、编号、代码、实体。
- Hybrid：兼顾语义和精确匹配，通常更稳。

**示范回答**

> 向量检索擅长处理语义相似，比如用户换一种说法也能召回相关文档。关键词检索擅长专有名词、ID、错误码、接口名这种精确匹配。实际系统里我更倾向 hybrid，再加 rerank。因为只用向量检索时，专有名词和短查询可能不稳定；只用关键词检索又容易漏掉同义表达。

## 8. RAG 能完全解决幻觉吗？

**面试官想听什么**

- 你不会过度吹 RAG。
- 你知道幻觉可能来自检索、prompt、模型和数据源。

**回答框架**

- RAG 降低幻觉，但不能消除。
- 检索不到、检索错、上下文太长、模型不忠实都会导致幻觉。
- 需要拒答策略、引用、评估和后处理。

**示范回答**

> RAG 只能降低幻觉，不能完全解决。因为模型可能拿错检索结果回答，也可能在检索结果不足时自行补全。  
>  
> 我的做法是让系统区分“没有检索到”和“检索到了但不确定”，并在 prompt 中要求不知道就拒答。同时记录 sources，方便排查。对于游戏 NPC 场景，还要避免模型把未解锁信息串起来推理成结论。

## 9. 如何设计长期记忆？

**面试官想听什么**

- 你能区分聊天记录、摘要、结构化记忆和向量索引。
- 你知道写入和检索都要控制。

**回答框架**

- 原始记录：完整审计。
- 摘要：压缩长期上下文。
- 记忆条目：结构化事实，可检索。
- 向量索引：语义召回。
- 写入策略：不是每轮都写，要去重、更新、过期。

**示范回答**

> 长期记忆不能简单等于完整聊天历史。完整历史适合审计，摘要适合压缩上下文，结构化记忆条目适合检索和更新。  
>  
> 我会把记忆分成用户事实、系统已承诺事项、未解决问题、偏好和关系信号等类型。写入时不一定每轮都写，可以定期总结或只在检测到重要信息时写。检索时要按用户、会话、业务对象过滤，避免串用户或串场景。

**结合 npc_app**

> `npc_app` 里长期记忆就是线程摘要加 memory items，memory items 同步到 Milvus。检索时按 `user_id`、`thread_id`、`npc_id` 过滤。

## 10. 短期记忆和长期记忆有什么区别？

**回答框架**

- 短期记忆：最近上下文，解决连续对话。
- 长期记忆：跨轮、跨时间保存的重要事实。
- 短期记忆通常直接进 prompt，长期记忆通常先检索再进 prompt。

**示范回答**

> 短期记忆主要服务当前对话连续性，比如上一轮用户说的“它”指什么。长期记忆服务跨时间连续性，比如用户偏好、已经达成的事实、NPC 已经透露过的信息。  
>  
> 技术上，短期记忆可以取最近 N 轮对话；长期记忆更适合摘要加结构化条目，再通过向量检索或规则检索按需召回。

## 11. 工具调用怎么设计？

**面试官想听什么**

- 你知道 tool schema、权限、错误处理和审计。

**回答框架**

- 工具要有明确 schema。
- 参数要校验。
- 工具有权限边界和超时。
- 高风险工具需要审批。
- 工具结果要结构化返回给模型。

**示范回答**

> 工具调用不是把所有 API 都交给模型。首先要设计清晰的 tool schema，告诉模型什么时候用、参数是什么、返回是什么。其次工具执行前要做参数校验和权限检查，执行时有超时、重试和错误码，执行后返回结构化结果。  
>  
> 如果工具会修改数据，比如删除、付款、发消息，我会加 human-in-the-loop 或二次确认，并记录审计日志。

## 12. Agent 调错工具怎么办？

**回答框架**

- 工具选择前：描述清晰、few-shot、路由限制。
- 工具执行前：参数校验、权限校验、风险分级。
- 工具执行后：结果验证、失败重试、回滚。
- 高风险：人工确认。

**示范回答**

> 我会把工具风险分级。只读工具可以自动调用，但要限流和超时；写操作工具必须有权限校验和二次确认；高风险操作需要人工审批。  
>  
> 另外工具结果不能完全相信模型解释，最好有结构化返回和后置校验。比如查询结果为空，就不允许模型编造结果。

## 13. Prompt injection 是什么？怎么防？

**面试官想听什么**

- 你知道用户输入和 RAG 文档都可能带恶意指令。
- 你知道工具型 Agent 风险更高。

**回答框架**

- Prompt injection：恶意文本试图覆盖系统指令。
- 间接注入：恶意内容藏在网页、文档、邮件、RAG 检索结果里。
- 防护：不可信上下文隔离、最小权限、工具 allowlist、输出过滤、审计。

**示范回答**

> Prompt injection 是用户或外部文档试图诱导模型忽略系统规则、泄露信息或错误调用工具。对 Agent 来说更危险，因为 Agent 可能有工具权限。  
>  
> 我会把用户输入和检索内容都视为不可信数据，只把它们作为资料，不作为指令。工具调用层做 allowlist、权限检查和高风险审批。输出层检查是否泄露 system prompt、密钥、内部实现或未授权信息。

## 14. 如何评估 Agent？

**面试官想听什么**

- 你不只看“感觉回答不错”。
- 你能拆成任务成功率、工具准确率、检索质量、生成质量。

**回答框架**

- 任务维度：成功率、完成步骤数、失败类型。
- RAG 维度：召回率、相关性、引用正确性。
- 生成维度：事实正确、忠实、格式稳定、人设一致。
- 工程维度：延迟、成本、错误率。
- 安全维度：越权、注入、隐私泄露。

**示范回答**

> 我会把 Agent 评估拆成多个层面，而不是只看最终答案。对于 RAG，看正确资料是否被召回；对于工具调用，看工具选择和参数是否正确；对于生成，看答案是否忠实于上下文、格式是否稳定；对于系统，看延迟、成本和错误率；对于安全，看是否能抵抗 prompt injection 和越权访问。  
>  
> 实践上可以建立 golden dataset，再结合线上 bad case 回流做回归测试。

## 15. LLM 输出不稳定，测试怎么写？

**回答框架**

- 不测完整自然语言逐字匹配。
- 测结构化字段、关键事实、禁止项、行为边界。
- 用 mock 固定模型输出测试业务逻辑。
- 用评估集测试模型质量。

**示范回答**

> LLM 应用测试要分层。业务逻辑层尽量 mock 模型输出，测试状态流转、数据库写入、工具调用、错误处理。模型质量层用评估集，检查关键事实、是否拒答、是否符合格式、是否违反禁止项，而不是逐字匹配。  
>  
> 对 Agent 来说，还要保存每一步 trace，这样失败时能知道是检索错、工具错、prompt 错还是模型生成错。

## 16. 如何降低成本和延迟？

**回答框架**

- 减少不必要调用。
- 路由小模型/大模型。
- 缓存 embedding 和检索。
- 控制上下文长度。
- 流式输出改善体验。
- 并行化独立步骤。

**示范回答**

> 成本和延迟可以从调用次数、模型大小、上下文长度和并发策略优化。比如先用轻量路由判断是否需要 RAG；embedding 和检索结果可以缓存；prompt 预算控制无关上下文；简单任务用小模型，复杂任务用大模型；输出层用 streaming 降低用户感知延迟。

## 17. 如何处理模型不知道答案的情况？

**回答框架**

- 检索为空时明确 unknown。
- prompt 要允许拒答。
- 不要让模型为了“有帮助”编造。
- 可以追问用户或给出下一步建议。

**示范回答**

> 我会在系统设计上允许模型不知道。比如 RAG 没有召回相关资料时，prompt 明确要求不要编造，可以回答“目前没有足够信息”。在业务场景里还可以转成自然语言，比如 NPC 不知道、回避、需要更多线索，而不是直接暴露系统检索失败。

## 18. 如何设计多 Agent？

**回答框架**

- 不要为了多 Agent 而多 Agent。
- 适合职责确实可拆分的任务。
- 常见模式：supervisor、planner-executor、critic、specialists。
- 风险：成本高、延迟高、错误传播、难调试。

**示范回答**

> 多 Agent 适合任务确实有多个专业角色，比如规划、执行、审核、搜索、代码修改。但如果单 Agent 或 workflow 能解决，就没必要引入多 Agent。  
>  
> 我会用 supervisor 控制全局，专业 Agent 只负责自己的任务，并且所有 Agent 输出都尽量结构化，方便验证和追踪。

## 19. 如果 Agent 回答错了，你怎么排查？

**回答框架**

按链路排查：

1. 用户请求是否解析正确。
2. 路由是否正确。
3. 检索是否命中。
4. rerank/过滤是否误删。
5. prompt 是否包含关键上下文。
6. 模型是否违背指令。
7. 后处理是否有问题。

**示范回答**

> 我会按 trace 排查，而不是直接改 prompt。先看输入参数和路由，再看检索结果和来源，然后看 prompt 最终内容，再看模型输出和后处理。如果检索没命中，改索引、chunk、query rewrite 或 rerank；如果 prompt 有信息但模型没用，改 prompt 或模型；如果模型输出正确但展示错误，查后处理和前端。

## 20. 如何解释你项目里的最大亮点？

**回答框架**

- 不要说“我用了很多技术”。
- 说清楚一个核心难点和你的设计。

**示范回答**

## 24. 高频追问速答

**Q: Agent 是否一定要有工具调用？**

> 不一定。工具调用是 Agent 常见能力，但 Agent 的核心是围绕目标进行状态化决策和执行。有些受控 Agent 主要通过检索、记忆和 workflow 完成任务。

**Q: RAG 和长期记忆有什么区别？**

> RAG 通常检索外部知识，长期记忆检索用户或会话相关历史。两者技术上都可以用向量库，但数据来源、权限边界和更新策略不同。

**Q: 为什么不把所有历史都放进 prompt？**

> 成本高、噪声大、容易干扰模型，而且上下文窗口不是可靠记忆系统。更好的方式是最近历史直接放，长期历史摘要化和检索化。

**Q: 如果模型输出 JSON 失败怎么办？**

> 用结构化输出能力或 schema validation；失败时做解析修复、重试或降级；关键业务不要直接信任未校验 JSON。

**Q: 如何防止不同用户记忆串了？**

> 所有记忆检索都必须带 user_id 或租户隔离字段，向量库 filter 和数据库查询都要做权限过滤，不能只靠 prompt。

**Q: 如何选择本地模型还是云模型？**

> 看隐私、成本、延迟和质量要求。本地模型适合隐私和成本可控场景，云模型通常质量和工具生态更强。也可以用路由策略混合。

## 2 分钟项目介绍版本

> 我最近做的是一个游戏 NPC 对话 Agent 后端。用户和 NPC 对话时，系统会先根据登录用户确认 thread，再加载最近 6 条对话作为短期记忆，同时读取线程摘要和长期记忆条目。接着系统会根据 NPC 身份、信任等级和剧情解锁等级去 Milvus 检索游戏知识，并检索该用户、该线程、该 NPC 的长期记忆。  
>  
> 编排上我用了 LangGraph，state 里保存 request、dialogue_history、summary、memory_items、chunks、prompt 和 answer。图里有三个节点：retrieve_context 负责 RAG，build_prompt 负责上下文规划和 prompt 预算，generate_answer 负责调用本地 Ollama 模型流式生成。生成完成后，系统保存聊天记录，并定期用 LLM 从新增对话里抽取长期记忆摘要和 memory items。  
>  
> 这个设计的重点是可控性。NPC 不能随便知道所有剧情，所以检索和 prompt 都要考虑 NPC 身份和剧情解锁。长期记忆也不能无限堆历史，所以我把它拆成摘要和可检索条目。当前不足是 checkpoint 还没接入，评估体系也可以继续完善。如果后续要做复杂多步任务或人工审批，我会把 LangGraph checkpoint 和 trace 观测补上。
