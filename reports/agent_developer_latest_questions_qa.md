# Agent 开发岗位高频问题回答稿

这份文档用于回答最近一轮搜索归纳出的 Agent 开发岗位常见问题。重点不是背概念，而是把回答组织成“理解问题 -> 工程设计 -> 项目例子 -> 风险和改进”。

## 0. 面试回答总模板

遇到 Agent/RAG/工具/记忆/评估类问题，可以用这个结构：

> 我会先明确业务场景，再选择 Agent 形态。生产里我不会默认追求完全自主 Agent，而是先用受控 workflow 保证可控性，再在局部引入模型决策。工程上会重点关注状态、记忆、工具权限、RAG 质量、评估、观测和安全。我的 `npc_app` 就是这个思路：用 LangGraph 编排单次 NPC 回复流程，用数据库和 Milvus 管理跨请求记忆，用 prompt 和检索过滤控制 NPC 可见信息。

## 1. Agent 和普通 LLM Chain 有什么区别？

**回答**

普通 LLM Chain 更像固定调用链：输入问题、拼 prompt、调用模型、返回答案。Agent 更强调带状态的执行闭环：它能根据目标读取上下文、选择工具、观察工具结果，并决定下一步行动。

但我不会把 Agent 理解成“越自由越好”。生产环境更关心可控、可观测、可回放和可评估。很多业务更适合 workflow + 局部 Agent 决策。

**结合项目**

`npc_app` 不是把用户问题直接发给模型，而是先加载 thread、最近对话、长期记忆和 RAG 知识，再用 LangGraph 执行 `retrieve_context -> build_prompt -> generate_answer`。所以它更像受控 workflow Agent。

## 2. 什么场景用 workflow，什么场景用自主 Agent？

**回答**

如果流程稳定、规则明确、风险较高，我倾向用 workflow。比如客服标准流程、财务审批、游戏剧情 NPC，这些都需要强约束。

如果任务开放、步骤不确定、需要动态选择工具，可以用更自主的 Agent。比如复杂研究、代码排错、跨系统自动化。

实际落地里常常是混合架构：外层 workflow 控制权限和边界，内部让 Agent 在有限范围内选择工具或策略。

**结合项目**

NPC 场景有剧情不剧透、人设一致性、信任等级等限制，所以我用了受控 workflow，而不是完全自主 Agent。

## 3. Planner、Executor、Memory、Tool、Observation 分别负责什么？

**回答**

Planner 负责拆解任务和决定下一步；Executor 负责执行计划；Memory 保存短期上下文和长期事实；Tool 是 Agent 访问外部世界的接口；Observation 是工具或环境返回的结果，Agent 根据 observation 再调整下一步。

工程上这几个组件不一定都由 LLM 完成。高风险或确定性的部分可以由代码完成。

**结合项目**

`npc_app` 里没有开放式 Planner，但有固定流程编排。Memory 包括最近对话、线程摘要和长期记忆条目；Tool 类能力主要是代码受控调用 Milvus、SQLite 和 Ollama；Observation 对应检索结果、sources 和模型输出。

## 4. ReAct、Reflection、Plan-and-Execute 有什么区别？

**回答**

ReAct 是 reasoning 和 action 交替进行，模型边思考边调用工具，再根据 observation 决定下一步。

Reflection 是让模型对自己的结果做反思或修正，适合生成质量改进，但会增加成本和延迟。

Plan-and-Execute 是先生成计划，再逐步执行，适合多步骤任务，但计划可能过时，需要动态调整。

**落地取舍**

如果任务短、风险高，我会优先固定 workflow。如果任务长、步骤不确定，可以考虑 Plan-and-Execute。如果答案质量要求高，可以在关键节点加 Reflection 或 reviewer。

## 5. 多 Agent 什么时候值得用？

**回答**

多 Agent 适合职责确实可拆分的任务，比如 planner、researcher、coder、reviewer、tester 各自有明确边界。它的好处是专业化和可组合。

但多 Agent 也会带来成本高、延迟高、调试困难、错误传播的问题。所以我不会为了显得复杂而上多 Agent。

**结合项目**

当前 `npc_app` 单 Agent workflow 已经足够。后续如果要做自动剧情生成或 NPC 行为审核，可以引入 writer Agent、reviewer Agent、evaluator Agent。

## 6. LangGraph 的 state 是什么？

**回答**

LangGraph state 是图执行过程中各节点共享和更新的数据结构。节点从 state 读取输入，返回部分字段作为更新。它可以保存请求、消息、工具结果、检索结果、prompt、answer、error 等。

state 不等于长期记忆。没有 checkpoint 时，state 主要在单次执行内流转；接入 checkpoint 后，state 可以用于中断恢复和跨步骤持久化。

**结合项目**

`npc_app` 的 `NpcGraphState` 里有 `request`、`dialogue_history`、`summary`、`memory_items`、`chunks`、`sources`、`system_prompt`、`user_prompt`、`answer`、`error`。它负责把检索、prompt 构建和生成节点串起来。

## 7. node、edge、state、checkpoint 各自解决什么问题？

**回答**

node 是一个处理步骤，比如检索、调用工具、生成答案。edge 决定节点之间怎么流转。state 是节点之间共享的数据。checkpoint 是把图执行状态保存下来，用于恢复、中断、回放或人工审批。

**结合项目**

`npc_app` 当前有三个 node：`retrieve_context`、`build_prompt`、`generate_answer`。edge 是固定顺序。state 传递上下文。checkpoint service 有预留，但当前没有接入 graph。

## 8. checkpoint 和业务数据库有什么区别？

**回答**

checkpoint 保存的是图执行状态，适合中断恢复、失败重试、人类审批、多步任务继续执行。

业务数据库保存的是业务事实，比如用户、订单、聊天记录、记忆、权限、审计日志。它需要支持查询、统计、权限过滤和长期维护。

二者不能简单替代。checkpoint 解决“执行过程怎么恢复”，业务数据库解决“业务数据怎么持久化和治理”。

**结合项目**

`npc_app` 的长期记忆保存在 `NpcThreadMemory`、`NpcMemoryItem` 和 Milvus 中，因为这些记忆需要按 `user_id/thread_id/npc_id` 查询和检索。checkpoint 当前不是必需。

## 9. 如何支持中断恢复、人类审批和失败重试？

**回答**

首先图执行要有明确 state 和节点边界。其次接入 checkpoint，把每个关键节点后的 state 持久化。遇到高风险操作时，图可以暂停，等待人工审批结果写回 state，再从暂停点继续。失败重试时，可以从最近 checkpoint 恢复，而不是从头执行。

工具调用要设计幂等性，避免重试导致重复写入。写操作还要有事务、审计和回滚策略。

## 10. RAG 的完整链路是什么？

**回答**

RAG 的完整链路包括：文档清洗、切块、metadata 设计、embedding、索引入库、查询改写、召回、过滤、rerank、上下文预算、prompt 构建、答案生成和评估。

真正落地时，metadata 和评估很关键。只做向量检索很容易召回看似相似但业务上不可用的内容。

**结合项目**

`npc_app` 的游戏知识 RAG 会结合 `npc_id`、`unlocked_story_level`、`trust_level`、`top_k`。长期记忆 RAG 会按用户、线程和 NPC 过滤，避免串记忆。

## 11. chunk size 和 overlap 怎么选？

**回答**

chunk size 没有固定答案。太小会丢上下文，太大会噪声多、成本高。overlap 能保留跨段语义，但会增加重复。

我的做法是先按文档结构切，比如标题、段落、规则块，再通过评估集验证正确 chunk 是否能被召回。如果召回经常缺上下文，就增大 chunk 或补标题；如果召回噪声太多，就缩小 chunk 或加 rerank。

## 12. 向量检索、关键词检索、hybrid search 区别是什么？

**回答**

向量检索擅长语义相似，用户换一种说法也可能召回。关键词检索擅长精确匹配，比如人名、道具名、错误码、接口名。hybrid search 结合两者，通常更适合生产。

如果业务里有很多专有名词，我不会只依赖向量检索，会结合关键词、metadata filter 和 rerank。

## 13. rerank 为什么重要？

**回答**

第一阶段召回通常追求 recall，会拿到一批可能相关的候选，但顺序不一定最适合回答。rerank 可以用更精细的模型或规则重新排序，把真正相关、权限正确、上下文完整的内容放前面。

**结合项目**

NPC 项目里 rerank 不只是相关性，还要考虑 NPC 身份、信任等级和剧情权限。低信任 NPC 不应该主动把多个线索串成完整真相。

## 14. RAG 为什么不能完全解决幻觉？

**回答**

RAG 只能降低幻觉，不能消除。因为检索可能没命中、召回结果可能错误、prompt 可能没表达清楚、模型也可能不忠实于上下文。

所以需要拒答策略、source 记录、上下文过滤、答案评估和 bad case 回流。不要把 RAG 当成万能事实保证器。

## 15. 如果检索不到内容，Agent 应该怎么回答？

**回答**

要区分业务场景。企业知识库可以直接说没有足够资料，并建议补充信息。游戏 NPC 场景不能暴露“检索失败”，可以自然地表现为 NPC 不知道、回避、要求玩家提供更多线索。

关键是不要让模型为了有帮助而编造。

**结合项目**

`npc_app` 里如果没有上下文，会生成未知回答，而不是让 NPC 硬编世界设定。

## 16. 短期记忆和长期记忆怎么设计？

**回答**

短期记忆保存最近上下文，用来处理连续对话、代词、省略和追问。长期记忆保存跨时间的重要事实，比如用户偏好、关系、承诺、未解决问题。

短期记忆可以直接进入 prompt；长期记忆应该摘要化、结构化，并按需检索。

**结合项目**

`npc_app` 短期记忆取当前 thread 最近 6 条聊天记录。长期记忆分为线程摘要和 memory items，memory items 会同步到 Milvus 做语义检索。

## 17. 为什么不能把所有历史都塞进 prompt？

**回答**

原因有四个：成本高、延迟高、噪声大、容易引入过期或冲突信息。长上下文模型也不能替代记忆系统，因为业务记忆还需要权限、更新、删除、审计和检索。

更合理的方式是：最近历史直接放，长期历史做摘要和结构化记忆，再按当前问题检索相关部分。

## 18. 长期记忆什么时候写入？怎么去重、更新、删除？

**回答**

长期记忆不一定每轮写入。可以在检测到重要事实时写，也可以累计几轮后总结写入。写入前要做结构化抽取和 schema 校验。

去重可以用规范化文本、embedding 相似度、实体 key 或业务唯一约束。更新时要保留 source 和 last_seen_at。删除要支持用户隐私和合规，比如用户要求删除记忆时，数据库和向量库都要清理。

**结合项目**

`npc_app` 默认累计 6 条新聊天记录后更新长期记忆，生成 summary 和最多若干 memory items。已有相同 content 会更新关键词、重要度和 last_seen_at。

## 19. memory 和 RAG 的区别是什么？

**回答**

RAG 通常指检索外部知识，比如文档、知识库、网页、产品手册。Memory 通常指系统从用户交互中积累的历史事实或偏好。

技术上二者都可以用向量库，但数据来源、权限边界、更新频率和删除要求不同。

**结合项目**

`npc_app` 的世界知识 RAG 来自游戏文档，长期记忆来自玩家和 NPC 的对话历史。

## 20. 如何防止不同用户的记忆串掉？

**回答**

不能靠 prompt 防串。必须在存储和检索层做隔离。数据库查询必须带 `user_id` 或租户 ID，向量库检索也要带 filter。工具调用也要从认证上下文拿用户身份，不能相信模型传入的用户 ID。

**结合项目**

长期记忆检索按 `user_id`、`thread_id`、`npc_id` 过滤，这是正确方向。

## 21. 长上下文模型出现后，还需要 memory 吗？

**回答**

需要。长上下文解决的是“能放更多内容”，但不解决记忆治理。长期记忆还需要压缩、更新、删除、权限隔离、审计、检索和冲突处理。

长上下文可以减少短期摘要压力，但不能替代业务级 memory。

## 22. tool calling / function calling 的原理是什么？

**回答**

模型根据工具描述和用户意图，生成结构化的工具调用请求，比如函数名和参数。应用代码拿到这个请求后执行真实工具，再把工具结果返回给模型，模型基于 observation 继续生成答案。

重点是：模型只是提出调用意图，真正执行必须由应用层控制，包括参数校验、权限检查、超时、重试和审计。

## 23. 如何设计 tool schema？

**回答**

tool schema 要清楚说明工具用途、什么时候使用、参数类型、必填字段、约束、返回结构和错误情况。参数描述要避免模糊，最好用枚举、范围和结构化字段。

高风险工具要拆细，不要给模型一个过于宽泛的万能工具。比如不要给 `run_sql(query)`，而是给受限的查询工具。

## 24. 工具参数错了怎么办？

**回答**

工具执行前必须做 schema validation 和业务校验。参数不合法时，不要直接执行，要返回结构化错误，让模型修正或向用户追问。

如果是写操作，还需要二次确认、权限校验和幂等 key，避免重复执行或误执行。

## 25. 工具超时、失败、返回脏数据怎么办？

**回答**

工具层要有超时、重试、熔断和降级。返回结果要结构化校验，不能把脏数据原样相信。失败时要把错误类型明确返回给 Agent，比如 timeout、permission_denied、not_found、invalid_args。

模型层要被告知不能编造工具结果。

## 26. Agent 调错工具，怎么防？

**回答**

第一，减少工具数量和重叠职责。第二，工具描述要清楚，提供正反例。第三，用路由或 allowlist 限制当前场景可用工具。第四，工具执行前做权限和风险校验。第五，高风险写操作加 human-in-the-loop。

## 27. 写操作工具是否需要 human-in-the-loop？

**回答**

看风险等级。只读工具通常可以自动执行。低风险写操作可以自动执行但要记录审计。高风险写操作，比如删除数据、转账、发外部消息、修改权限，应该有人类确认或至少二次确认。

## 28. MCP 是什么？解决什么问题？

**回答**

MCP 可以理解为一种让模型应用连接外部工具和数据源的标准协议。它把工具、资源和提示等能力以统一方式暴露给 Agent，减少每个工具都单独适配的成本。

但 MCP 不是安全魔法。接入 MCP 后，仍然要做工具 allowlist、权限控制、沙箱、审计和用户确认。

## 29. MCP 和普通 API / OpenAPI 有什么区别？

**回答**

普通 API/OpenAPI 主要面向程序调用，描述接口路径、参数和响应。MCP 更面向模型应用，把工具和资源以 Agent 可发现、可调用的方式提供出来。

它的价值是统一 Agent 连接外部能力的方式，但风险是工具能力暴露更方便后，越权和注入风险也更需要管理。

## 30. MCP 工具有哪些安全风险？

**回答**

风险包括：工具描述被污染、工具冒充、过度授权、prompt injection 诱导调用危险工具、工具返回恶意指令、跨用户数据泄露。

防护方式包括：只接入可信 MCP server；工具 allowlist；按用户授权；沙箱执行；高风险工具确认；记录工具调用审计；把工具返回当作不可信数据。

## 31. 什么是 prompt injection？

**回答**

Prompt injection 是用户或外部内容试图覆盖系统指令，诱导模型泄露信息、忽略规则或错误调用工具。

Direct injection 是用户直接输入恶意指令。Indirect injection 是恶意指令藏在网页、文档、邮件、RAG 检索结果或工具返回里。

## 32. RAG 文档里藏恶意指令怎么办？

**回答**

检索内容必须被视为不可信资料，而不是指令。prompt 中要明确区分系统指令和检索资料。检索入库前可以做文档清洗和风险扫描。生成时要限制模型遵循资料中的事实，而不是遵循资料中的命令。

如果 Agent 有工具权限，工具调用不能由检索文档直接触发，必须经过权限和策略校验。

## 33. 工具返回结果里藏恶意指令怎么办？

**回答**

工具返回也要视为不可信 observation。模型可以读取其中的数据，但不能把其中的指令当成系统命令。对工具结果做结构化解析，只提取需要字段，避免把完整 HTML、邮件或脚本直接塞给模型。

高风险工具调用要由策略层控制，而不是让模型根据工具返回里的文字自行决定。

## 34. 如何防止泄露 system prompt、API key、用户隐私？

**回答**

API key 不应该进入 prompt，应该只在服务端环境变量或密钥管理系统中。system prompt 不能依赖“请不要泄露”来保护，还要做输出过滤和权限隔离。

用户隐私要在存储、检索、日志和工具调用层隔离。日志里避免记录敏感明文，必要时做脱敏。

## 35. 如何限制 Agent 的文件、数据库、浏览器权限？

**回答**

原则是最小权限。文件访问限制到工作目录或允许列表；数据库工具限制到预定义查询或只读视图；浏览器访问限制域名和动作；所有写操作都要审计，高风险操作要审批。

不要给模型任意 shell、任意 SQL、任意文件系统权限。

## 36. 如何评估一个 Agent 是否能上线？

**回答**

我会从五类指标评估：任务成功率、工具调用准确率、RAG 检索质量、生成质量、安全可靠性。

任务成功率看最终是否完成用户目标。工具调用准确率看工具选择和参数是否正确。RAG 看正确资料是否召回、答案是否忠实。生成质量看事实正确、格式稳定、风格符合。安全看是否越权、泄露隐私、受到 prompt injection 影响。

## 37. 任务成功率、工具调用准确率、检索命中率、幻觉率怎么定义？

**回答**

任务成功率是任务最终达成的比例。工具调用准确率是工具选择正确且参数正确的比例。检索命中率是正确证据是否出现在 top_k 结果中的比例。幻觉率是答案包含无依据或错误事实的比例。

这些指标要结合人工标注和自动评估，不能只靠模型自评。

## 38. 如何构建 golden dataset？

**回答**

先从核心用户场景抽样，覆盖正常问题、边界问题、权限问题、无答案问题、恶意输入和历史上下文问题。每条样本要包含输入、期望行为、可接受答案标准、必须引用的证据、禁止出现的内容。

上线后把 bad case 回流到 golden dataset，形成回归测试。

## 39. LLM 输出不稳定，自动化测试怎么写？

**回答**

不要逐字匹配自然语言。应该测试结构化字段、关键事实、禁止项、引用来源、工具调用序列和状态变化。业务逻辑测试可以 mock LLM 输出；模型质量测试用评估集和 rubric。

**结合项目**

NPC 项目可以测试：是否泄露未解锁剧情、是否符合 NPC 人设、是否使用了正确 memory、是否在无资料时拒绝编造。

## 40. Agent trace 应该记录哪些信息？

**回答**

至少记录 request_id、user_id、thread_id、模型、prompt 版本、检索 query、召回 sources、rerank 结果、工具调用、工具参数、工具结果摘要、节点耗时、token 用量、最终答案和错误信息。

trace 的目标是让失败可以复现，让成本和质量可以分析。

## 41. 如何区分是检索错、prompt 错、工具错还是模型错？

**回答**

看 trace 分层定位。检索错表现为 sources 不相关或缺失；prompt 错表现为关键信息没有进入 prompt 或指令冲突；工具错表现为工具选择、参数或返回异常；模型错表现为 prompt 里有正确证据但模型没遵守。

不要一上来就改 prompt，要先定位是哪一层失败。

## 42. 如何做 streaming？

**回答**

后端可以用 SSE、WebSocket 或 NDJSON stream。关键是把状态事件、工具事件、answer delta 和 done 事件区分开。这样前端既能展示生成中的文本，也能展示检索中、调用工具中、完成或失败。

**结合项目**

`npc_app` 用 FastAPI `StreamingResponse` 返回 NDJSON，事件包括 thread、sources、answer_delta、done 和 error。

## 43. 如何降低延迟和 token 成本？

**回答**

减少不必要模型调用；用路由判断是否需要 RAG；缓存 embedding 和常见检索；限制 prompt budget；简单任务用小模型，复杂任务用大模型；独立步骤并行化；流式输出降低感知延迟。

## 44. 如何选择本地模型和云模型？

**回答**

看质量、成本、延迟、隐私和可控性。本地模型隐私和成本可控，但质量、并发和维护压力可能更大。云模型通常能力强、工具生态好，但成本和数据合规要评估。

实际可以混合：低风险简单任务走本地或小模型，高复杂任务走更强模型。

## 45. 如何做 observability？

**回答**

要有日志、指标和 trace。日志记录关键事件，指标统计延迟、错误率、token、工具成功率、检索命中率，trace 串起一次 Agent 执行的完整链路。

最好能按 prompt 版本、模型版本、用户场景和工具类型分析质量。

## 46. 如何做 prompt versioning？

**回答**

prompt 要像代码一样版本化。每次修改 prompt 都要记录版本、变更原因和评估结果。线上请求记录 prompt version，方便回溯。重要 prompt 修改要跑回归评估，不要直接上线。

## 47. 如何上线后监控质量？

**回答**

上线后要监控业务指标、模型指标和安全指标。业务指标包括任务完成率和用户反馈；模型指标包括幻觉率、拒答率、格式错误率；系统指标包括延迟、错误率、成本；安全指标包括越权、敏感信息输出、prompt injection 命中。

还要建立 bad case 收集和回归机制。

## 48. 你的 npc_app 为什么是受控 workflow Agent？

**回答**

因为游戏 NPC 对话的核心不是最大自由度，而是一致性和边界控制。NPC 不能随便知道所有剧情，不能泄露系统实现，也要保持人设和信任等级。

所以我用 LangGraph 固定流程：先检索上下文，再构建 prompt，再生成回答。这样每一步可控、可记录、可扩展。

## 49. 为什么 state 里放 dialogue_history、summary、memory_items、chunks？

**回答**

这些字段分别对应不同层次的上下文。

`dialogue_history` 是短期记忆，处理连续追问。`summary` 是线程摘要，压缩长期上下文。`memory_items` 是可检索长期记忆，保存玩家事实、NPC 已透露信息、未解决问题等。`chunks` 是世界知识 RAG 结果，提供游戏设定依据。

放在 state 里，是为了让检索、prompt 构建和生成节点共享同一份结构化上下文。

## 50. 为什么当前不用 checkpoint？

**回答**

当前一次 NPC 回复流程很短，单次请求内就执行完：检索、构建 prompt、生成回答。跨请求记忆已经由业务数据库和 Milvus 负责。

checkpoint 更适合中断恢复、人工审批、多步任务继续执行。当前项目有 checkpointer service 预留，但还没有接入 graph。后续如果要做复杂工具调用或人工审批，再接入 checkpoint 会更有价值。

## 51. 短期记忆为什么只取最近 6 条？

**回答**

这是成本、相关性和上下文长度之间的权衡。最近几轮最能解决代词、省略和连续追问。更早的信息如果重要，会进入长期摘要或 memory items。

后续可以改成动态策略，根据 token budget、问题类型和历史相关性决定保留多少轮。

## 52. 长期记忆为什么用 summary + memory items + Milvus？

**回答**

summary 适合提供整体连续性，但不适合精确检索。memory items 适合保存结构化事实，比如玩家偏好、未解决问题、NPC 已透露内容。Milvus 适合根据当前问题做语义召回。

三者组合能避免无限堆聊天历史，同时支持跨轮记忆和相关记忆检索。

## 53. Milvus 检索失败怎么降级？

**回答**

世界知识检索失败时，可以返回空上下文并通过 stream 输出错误事件，让回答走不知道或保守策略。长期记忆检索失败时，可以 fallback 到数据库 memory items，用关键词 overlap、importance、last_seen_at 做简单排序。

核心是不要因为向量库失败导致整个服务不可用，也不要让模型编造检索结果。

## 54. 如何防止 NPC 说出未解锁剧情？

**回答**

要多层防护。检索层根据 `npc_id` 和 `unlocked_story_level` 过滤；规划层过滤敏感内容；prompt 层强调 NPC 只能使用当前可见信息；评估层构造未解锁剧情测试集，检查是否剧透。

只靠 prompt 不够，权限控制要前移到检索和数据层。

## 55. 如何评估 NPC 是否符合人设？

**回答**

可以建立 NPC 人设 rubric，包括语气、知识边界、信任等级、禁说内容、是否承接历史、是否符合剧情阶段。评估样本要覆盖不同 NPC、不同关系阶段、不同剧情解锁等级。

自动评估可以先用规则检查硬性禁区，再用 LLM judge 评估风格和一致性，重要样本需要人工复核。

## 56. 如果回答不准，你怎么定位问题？

**回答**

我会按链路定位：请求参数是否正确；短期历史是否取对；长期记忆是否召回；Milvus chunks 是否相关；rerank 和权限过滤是否正确；prompt budget 是否裁掉关键内容；模型是否违背 prompt。

因为 LangGraph 节点边界清晰，可以记录每个节点的输入输出，定位会比较直接。

## 57. 如果要加查背包/任务/地图工具，你会怎么设计？

**回答**

我会先定义工具边界和权限。查背包、任务、地图这类工具通常是只读，可以自动调用，但必须从认证上下文拿 user_id，不能让模型传入任意 user_id。

tool schema 要限制参数，比如 `get_inventory()` 不需要 user_id 参数，只读取当前用户。写操作如消耗道具、推进任务必须二次确认或服务端规则校验。所有工具调用要记录 audit log。

## 58. 面试最后的 60 秒总结

可以这样收尾：

> 我对 Agent 开发的理解是，它不是简单调一个大模型，而是一个状态化、可控、可评估的工程系统。核心模块包括 workflow/state、RAG、memory、tools、evaluation、observability 和 safety。我的 `npc_app` 用受控 workflow Agent 做 NPC 对话：LangGraph 管单次执行状态，数据库和 Milvus 管跨请求记忆，RAG 和 prompt 控制 NPC 可见信息。当前项目还可以继续补 checkpoint、工具权限、评估集和安全防护，这些也是我认为生产级 Agent 最重要的方向。
